# 运营数据工作台（ops-workbench）

把几份**每天要维护的 Excel**（直播场次、订单、库存、商品货盘）变成**一个只读网页**：左边切视图，右边查数据，图片直接显示，分类自动补全。

给电商运营/直播团队用的。它解决的不是"分析"，而是**"今天这张表到底什么情况"**——四张表来回导、来回对照，一天要花一两个小时的事。

> 这个项目是从一个真实在用的内部工作台去敏而来的：**逻辑保留，业务内容全部抽成配置**。
> 仓库里没有任何真实业务数据、公司标识或原表结构，示例数据由 `demo/generate_demo.py` 合成。
> 内部版的迁移脚本（含原路径）不随仓库发布。

## 五个设计决策（每个都对应一个真实踩过的坑）

| 决策 | 为什么 |
|---|---|
| **字段白名单** | 配置里逐视图列出**允许外发**的字段，其余列（成本价、手机号、内部备注）服务端根本不读。数据外发风险从"记得别传"变成"结构上不可能传" |
| **只绑 127.0.0.1 + 校验 Host/Origin/Sec-Fetch-Site** | 本机服务最容易被忽略的两个坑：DNS rebinding（恶意域名解析到 127.0.0.1）和跨站 POST。三项校验不过直接 403 |
| **防脏读** | 读前读后各取一次 `stat`，文件在读取期间被改过就报错。宁可让你刷新，也不返回半新半旧的快照（运营看错数字的代价很高） |
| **图片内容寻址** | 图片按 URL 的 SHA-256 存成 `.img`，天然去重；缺图明确标 `missing`/`unavailable`，**不拿相似商品凑图** |
| **分类分级兜底** | 顺序是：源表已有值 → 名称明示词 → 商业别名 → 材料常见色范围 → 未分类。每一级都能说出依据，且从不声称"鉴定" |

## 快速开始

```bash
git clone https://github.com/19X19BTR/ops-workbench.git
cd ops-workbench
pip install -r requirements.txt          # 只有 openpyxl + Pillow

cp config/config.example.json config/config.json
python demo/generate_demo.py             # 生成合成示例数据
python server.py                         # 打开 http://127.0.0.1:8765
```

## 配置：唯一需要你改的地方

```json
{
  "views": {
    "catalog": {
      "title": "商品分类货盘",
      "file": "demo/catalog.xlsx",        // 你的 Excel
      "sheet": "商品分类明细",             // 可选：指定工作表
      "whitelist": ["商品编码", "优先商品名称", "类型候选"],   // 能外发的字段
      "imageFields": ["图片链接"]          // 哪一列是图片 URL
    }
  },
  "stockViews": [{"sheet": "商品库存", "label": "商品库存"}],
  "classify": { "type": [...], "material": [...], "colorAliases": [...] }
}
```

- `file` 支持相对项目根或绝对路径；`config/config.json` 已在 `.gitignore` 里，**你的真实表结构和路径不会进仓库**
- **分类词库**：`config/knowledge.shared.json` 是经运营团队授权提供的去敏词库（52 个材质、9 个类型、颜色别名与材料色范围规则），已合并进示例配置，复制即可用；它只含品类/材质/颜色检索词，不含商品编码、价格、库存或客户信息
- `whitelist` 是硬边界：不在列表里的列，接口里不会出现
- `classify` 是检索/分类词库，每项是 `[标签, 正则]`；正则不分大小写（`S925` 这种英文才匹配得到）

## 能做什么

| 视图 | 内容 |
|---|---|
| 直播数据 | 场次、时长、消耗、ROI、GMV、GPM、观看/点击/转化，含趋势图 |
| 订单列表 | 主/子订单、商品、金额、状态、售后 |
| 商品库存 | 实际库存/订单占有/可用数、仓位、分仓；支持多个仓位视图切换 |
| 商品分类货盘 | 从源行出发查商品，类型/材质/颜色三维筛选，含"未识别字段"筛选与列表/卡片两种视图 |

分类词库规模（`config/knowledge.shared.json`，经授权去敏）：**9 类类型词 / 52 类材质词 / 9 条颜色别名 / 7 条材料色规则 / 4 条材料色范围**。

分类规则示例（来自 `config.example.json`）：

```
紫水晶手串 8mm      → 类型:手串  材质:水晶  颜色:紫
茶晶单圈 10mm       → 颜色:茶棕灰（按颜色名称推定）
藕粉 单圈 10mm      → 颜色:粉（按名称推定）
碧玺圆珠 4mm        → 颜色:多色系（碧玺为多色材料，不硬判单色）
多宝手串 MB20260001 → 颜色:多宝（命中明确商品编码）
未知商品 X-001      → 类型:不适用（原料名称线索） / 材质未分类 / 颜色未分类
仿水晶手串          → 颜色未分类（仿制/处理品不做颜色推定）
莫粉圆珠 6mm        → 材质:莫粉（名称分类）
绿松石桶珠 5mm      → 颜色:蓝绿范围（按松石名称推定）
```

## 测试

```bash
python -m unittest discover -s tests -t .   # 服务端 26 项
node tests/classify.test.cjs                # 分类逻辑 24 项
```

服务端测试覆盖：配置校验（缺 views / 未知视图 / 空白名单）、字段白名单过滤（成本价/手机号/内部备注不外发）、图片三态、**防脏读**、403 边界（错误 Host、跨站 Origin、非 JSON 的 POST）、404、响应头。

分类测试用 `vm` 把页面脚本跑起来，不依赖浏览器，改词库后重启测试就能验证规则。

## 和"BI 工具"的区别

- **不汇总跨来源**：直播、订单、库存各自独立展示，不合并成"总 GMV"——来源口径不同，加起来就是错的
- **只读**：除了"在访达里定位源文件"，不改任何表
- **承认不确定**：`待核` 不当成已分类，缺图不补图，分类不叫鉴定

## 已知限制

1. 仅本机使用（`127.0.0.1`），没有登录体系——设计如此，不要暴露到公网
2. 单进程 + `openpyxl` 读整表，几十 MB 的表首次读取要几秒
3. 「在访达里定位文件」是 macOS 实现，其他平台返回 `platform` 字段供前端提示
4. 分类词库需要业务自己维护，代码不联网、不猜矿物成分
5. 只支持 `.xlsx`（老式 `.xls` 需先转格式）
